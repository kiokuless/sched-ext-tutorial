# CPU ごとの DSQ

本編では偶数用と奇数用の二つの共有 DSQ を作り、どの CPU も両方の待ち行列からタスクを受け取れるようにした。
空いた CPU へ仕事を渡しやすい一方、タスクが前回と異なる CPU で実行される機会もある。
CPU を移ると、前回の CPU で温まっていたキャッシュをそのまま再利用できない場合がある。

CPU ごとに待ち行列を用意すれば、同じ CPU で動かしてキャッシュを再利用する方針を表現できる。
ただし、空いた CPU への仕事の分散も考える必要があり、どちらを優先するかは workload によって変わる。

## 設計の違い

CPU 間で共有する構成と、CPU ごとに待ち行列を持つ構成を概念的に比べると次のようになる。

この構成の違いだけで「どちらが速いか」は決まらない。
短いタスクが大量に到着し、空いた CPU をすぐ使いたい workload と、同じタスクが繰り返し CPU を使い、キャッシュの再利用が効く workload では評価が変わる。

右の図で B が終了すると、CPU 1 は空くが、A と C は CPU 0 側の列に残る。
CPU 1 にも A や C を実行させるには、ほかの CPU の列から取り出す規則が必要になる。
同じ CPU で動かしてキャッシュを再利用する効果と、負荷の偏りを解消する効果を、対象の workload で比べる。

## 何を測るか

比較実験を作るなら、本編と同じく一度に変える条件を一つにする。
タイムスライスは固定し、キューの配置だけを変える。

タスクの配置と性能の関係を調べるため、次の値を記録する。

- CPU migration の回数
- タスクごとの実行時間や遅延
- workload 全体の throughput
