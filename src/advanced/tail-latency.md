# tail latency の測り方

本編の実験は15回の起床で行い、p99 を評価しないと述べた。
この章では、その制約を解消する測り方を扱う。
15回の起床では、最悪に近い一回を見つけることはできても、p99を安定して推定できない。
100ミリ秒周期で標本数を増やし、複数回の試行を行う。

標本が増えた今度は、分布の要約の仕方が問題になる。
平均値は全標本を一つの値へ均す。
一部のタスクだけが長く待たされても、残りが速ければ平均値の変化は小さい。
そこで p50、p95、p99を並べ、分布の中央と裾を分けて見る。

ただし、一回の p99だけで scheduler の優劣を断定することもできない。
ホスト負荷、VM の停止、バックグラウンド処理によって外れ値が生じるため、同じ条件を複数回実行し、試行間のばらつきも記録する。

数値で裾の外れ値が見つかったら、その時刻に何が起きていたかをトレースで裏付けられる。
`scxtop trace` は wakeup、`sched_switch`、migration、DSQ のイベントを Perfetto trace として保存できる。
数値に外れ値が現れた時刻をトレースへ戻すと、どのタスクが CPU を保持していたかを調べられる。

scxtop はコアのハンズオン環境には含まれない。
必要な場合は `cargo install scxtop --version 1.1.3 --locked` で任意に導入する。
