# tail latency の測り方

本編で数行の時刻を観察しただけでは、大きな遅れがあることは分かっても、その頻度を細かく推定できない。
遅延分布の上位側にある遅い部分を **tail latency** と呼ぶ。
その部分を調べるには、標本数と試行回数を増やす必要がある。

## 測定条件を広げる

本編の `tools/sleep.py` は、1秒眠る処理を繰り返し、標本間の経過時間を表示する。
その間隔には、sleep に加えて表示処理の時間も含まれる。
100 ミリ秒の sleep を 3,000 回繰り返す場合、眠る時間だけで 300 秒あり、遅れた分だけ測定も長くなる。
本編と同じ端末操作で測る場合は、観察を続ける間、計算タスクも動かしておき、実験後に両方を止める。

繰り返し測る作業を自動化する場合は、`make bench` も使える。
このコマンドは別途用意した Rust の負荷生成器を使い、CPU 0 に計算タスクを二つ置いて、sleep を5回実行する。
負荷生成器の `elapsed_ms` は各 sleep の前後の経過時間、`late_ms` はそこから指定時間を引いた値である。
終了後は負荷とスケジューラを停止する。
本編は計算タスクが一つなので、待ち時間の条件が異なる。
自作スケジューラが停止している状態で、Mac 側から実行する。

```console
make bench CASE=fair
make bench CASE=step STEP=02
make bench CASE=step STEP=03
```

この自動測定では計算タスクが最長60秒で終了する。
`scripts/guest/bench.sh` を変更して測定を長くする場合は、この時間も延ばす。
二つの計算タスクで測った [2秒スライス](../measurements/2026-09-07/long.txt)と[10ミリ秒スライス](../measurements/2026-09-07/short.txt)の参考記録も残している。

一方、固定した予定時刻からの遅れを測る場合は、負荷生成器の `periodic` を使う。
たとえば `periodic --period-ms 100 --samples 3000` は、100 ミリ秒刻みの予定時刻に対する遅れを記録する。
`--sched-ext` を付けると自作スケジューラの対象になる。
大きく遅れた場合は、すでに過ぎた予定時刻の標本をほとんど眠らずに続けて記録するため、各標本が別々の wakeup に対応するとは限らない。
この測定と、毎回の sleep にかかった時間の測定を混同しない。

以前の共有 DSQ と `periodic` を使った測定は、[2026年9月6日の記録](../measurements/2026-09-06/long.txt)に残している。
記録内の STEP 番号は当時の構成を示し、現在の完成例の番号とは異なる。

## 分布の中央と裾を分ける

平均値は全標本を一つの値へ均す。
一部のタスクだけが長く待たされても、残りが速ければ平均値の変化は小さい。
そこで p50、p95、p99 を並べ、分布の中央と裾を分けて見る。
ここで p99 は、標本を小さい順に並べたときに約 99% がそれ以下になる値である。
集計方法も記録し、たとえば nearest-rank 法なら、標本数を N として `ceil(0.99 × N)` 番目を使う。
3,000 標本なら 2,970 番目だが、それより上の標本は 30 個しかない。

ただし、一回の p99 だけで scheduler の優劣を断定することもできない。
ホスト負荷、VM の停止、バックグラウンド処理によって外れ値が生じるため、同じ条件を複数回実行し、試行間のばらつきも記録する。

## 遅れた区間をトレースする

分布から分かるのは遅れの大きさと頻度であり、その原因までは確定しない。
任意で導入できる `scxtop trace` は wakeup、`sched_switch`、migration、DSQ のイベントを Perfetto trace として保存できる。
wakeup イベントから対象タスクが CPU に載るまでを追うと、待っている間にどのタスクが走っていたかを調べられる。
ただし、現在の負荷生成器の CSV には標本番号と遅延しかなく、トレースと直接照合できる時刻や PID はない。
照合する実験では、それらを記録するよう負荷生成器を拡張し、両方の時計の対応も確認する必要がある。
