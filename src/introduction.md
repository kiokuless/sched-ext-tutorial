# はじめに

`sleep(1)` を呼んでも、必ず 1 秒後に処理を再開できるわけではない。
タイマーが満了することと、CPU を割り当てられることは別だからである。
同じ CPU を別のプロセスが使っていれば、1 秒が過ぎた後にも順番待ちが生じる。

この待ち時間は、実行中のプロセスにどれだけ CPU 時間を割り当てるかで変わる。
本書では、計算を続けるプロセスと `sleep(1)` を繰り返すプロセスを一つの CPU で動かし、割り当てる時間を変えて、処理の再開がどれだけ遅れるかを確かめる。

## タイマー満了から実行再開まで

Linux が CPU を割り当てる実行単位を **タスク** と呼ぶ。
アプリケーションの各スレッドが一つのタスクに対応するので、それぞれが 1 スレッドのプロセス A と B は、二つのタスクとして扱われる。
一つの論理 CPU で同時に実行できるタスクは一つであり、どちらを動かすかを決めるのが **スケジューラ** である。

A が `sleep(1)` でタイマーを待っている間は、A に CPU を割り当てる必要がなく、B が計算を進められる。
タイマーが満了すると、A は再び実行可能になる。
このように、I/O やタイマーなどの待ち状態から実行可能になる状態変化を **wakeup** と呼ぶ。

ただし、wakeup の時点で A の CPU が予約されているわけではない。
B に長く CPU を使わせる方針なら、A は実行可能になった後も、CPU が割り当てられるまで待つ。

OS は、中断するタスクのレジスタなどの実行状態を保存し、次のタスクの状態を復元する。

## BPF の関数を sched_ext に登録する

このハンズオンでは、CPU の候補を選ぶ関数や、タスクを待ち行列へ入れて CPU 時間を割り当てる関数を書く。
これらをカーネル内で実行するために使うのが **BPF** である。
BPF プログラムは、カーネルが定めた形式と制約に従って記述し、ユーザ空間からカーネルへ読み込める。

Linux の **`sched_ext`** は、この BPF を使って CPU スケジューラを実装する仕組みである。
CPU の候補を選ぶときや、次に実行するタスクを求めるときに、カーネルが登録された関数を呼び出す。
呼ばれる場面に応じて登録するこうした関数を **callback** と呼ぶ。
callback の実装を変えれば、カーネルを書き換えて再起動せずに、スケジューリングの方針を差し替えられる。

BPF プログラムをカーネルへ読み込むのは、ユーザ空間で動く **loader** の役割である。
ロード時にはカーネルの **verifier** が、そのプログラムを実行してよいか検査する。
検査を通過して `sched_ext` に接続した後は、カーネル内で callback が呼ばれ、許可された機能を使ってタスクの投入先や CPU 時間を指定する。
本書では callback を BPF C で、loader を Rust で書く。

## 想定する読者

Rust でプログラムを書いた経験があり、大学で学ぶ OS の基礎を知っている読者を想定する。
Linux カーネル、BPF、`sched_ext` の実装経験は前提にしない。

操作には Linux のコマンドラインを使い、スケジューラを編集するときには短い C のコードを読む。
OS の基礎は必要なところで復習し、BPF のマクロや Linux 固有の呼び出し条件は、実際のコードと対応させて説明する。

## 作るスケジューラ

本編で作るのは、先に並んだタスクから扱う **FIFO** のスケジューラである。
まず、タスクに割り当てる CPU 時間を変えて sleep の再開時刻を測る。
その後、待ち行列を分けて、プロセス間の CPU 時間の配分を変える。
一度に変える条件を一つに絞り、コードの変更と観測結果を対応させていく。

重みに応じた公平性、優先度、キャッシュや NUMA を考慮した配置は、発展編へ進むときの設計課題とする。
本文で定義した用語は、後から参照できるよう[用語集](appendix/glossary.md)にまとめている。

`sched_ext` の ABI には安定性の保証がないため、本書は Ubuntu 26.04 の標準カーネルと `scx` v1.1.3 の組み合わせで検証している。
異なる組み合わせでは、callback や BPF から呼ぶカーネル関数の名前が変わる可能性がある。

## 実行上の注意

自作スケジューラは、配布する Multipass VM の中で root 権限を使って動かす。
日常利用している Linux ホストでは実行しない。

BPF verifier と、実行中のタスクの停滞を検出する **watchdog** は多くの失敗を止めるが、任意のスケジューラを安全に実行できるという保証ではない。
実験の影響を VM 内に限定するためにも、指定の環境を使う。
