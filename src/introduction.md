# はじめに

`sleep(1)` を呼び出したプロセスは、およそ1秒後に実行を再開する。
普段はそれで困らない。
ところが、タイマーが満了してプロセスが実行可能になっても、CPU を割り当てるスケジューラが後回しにすれば、再開はさらに遅れる。

どれだけ遅れるかは、自分で決められる。

Linux の **`sched_ext`** は、BPF で記述した CPU スケジューラを実行時に読み込む仕組みである。
カーネルを変更して再起動しなくても、タスクをどの順番で、どの CPU で、どれだけの時間動かすかを試せる。

このハンズオンでは、小さな FIFO スケジューラを動かし、1秒周期のタスクを意図的に遅らせる。
次にタイムスライスを短くし、遅延とコンテキストスイッチ数の変化を観測する。
最後には、壊れたスケジューラを watchdog に停止させる。

## 想定する読者

次の知識を前提とする。

- C と Rust のコードを読んだ経験がある
- Linux のコマンドラインを操作できる
- 一つの CPU コアが同時に実行できるタスクは一つであり、コンテキストスイッチによって並行に見せていると理解している

BPF、カーネル開発、スケジューラの実装経験は前提にしない。

## 到達点

完了時には、次の作業を自力で再現できる状態を目指す。

- `sched_ext_ops` の主要な callback を読んで、タスクが CPU に載るまでを追う
- 独自の dispatch queue とタイムスライスを持つ scheduler をロードする
- wakeup 後の遅延とコンテキストスイッチ数を測る
- 観測値が変わった理由を、変更した方針と結び付けて説明する

`sched_ext` の ABI には安定性の保証がないため、この教材は Ubuntu 26.04 の標準カーネルと `scx` v1.1.3 の組み合わせで検証している。
異なる組み合わせでは callback や kfunc の名前が変わる可能性がある。

## 実行上の注意

自作 scheduler は、VM 内で root 権限を使って動かす。
BPF verifier と `sched_ext` の watchdog は多くの失敗を止めるが、「任意の scheduler を安全に実行できる」という保証ではない。
日常利用している Linux ホストではなく、配布する Multipass VM を使う。
