# A が増えても B の速さを保つ

A チームと B チームで、一つの CPU を使っている。
最初は A1 と B1 が一つずつ動き、ほぼ同じ速さで計算が進む。
5秒ほど経つと、A チームに A2 と A3 が加わる。
B1 自身は何も変えていないのに、進捗バーが遅くなる。

前の課題では、A と B の二つを区別して実行時間を変えた。
今回は、途中でプロセスの数が変わる。
人数が増えた側へ順番が多く回る動きを、自分の共有 DSQ で変えてみよう。

## 今回の課題

> A チームのプロセスが増えても、B1 の進む速さを追加前とほぼ同じに保つ。<br>
> A 用と B 用の二つの共有 DSQ を使い、全タスクに同じ長さのスライスを渡す。<br>
> A の全員にも順番を回し、計算を進める。

計算プログラムや CPU affinity は変更せず、`lab/src/bpf/main.bpf.c` を編集する。
プロセスの名前は `team_a1`、`team_a2`、`team_a3`、`team_b1` である。
PID や A の人数をコードに固定せず、名前からチームを判断する。

| 時点 | 動いているプロセス | 観察するもの |
|---|---|---|
| 開始直後 | A1、B1 | B1 の進む速さ |
| 約5秒後 | A1、A2、A3、B1 | B1 の速さが追加前からどう変わったか |

## まず B1 が遅くなる様子を見る

前の実験のスケジューラと負荷を終了してから、Mac 側のリポジトリ直下で実行する。

```console
make team-race STEP=03
```

`STEP=03` は、全員をグローバル DSQ の一つの FIFO に入れ、同じ10ミリ秒のスライスを渡す完成例である。
実験コマンドは partial mode で起動し、全員を CPU 0 に揃える。
別の CPU で測る場合は `RACE_CPU=1` のように指定できる。

最初に、A1 と B1 の名前、PID、進捗バーが現れる。
A2 と A3 はまだ起動しておらず、`not started` と表示される。
約5秒後に `Adding team_a2, team_a3` が表示され、新しく起動した二つの PID とバーが加わる。

各行の `%` は、同じ計算量のうち終えた割合である。
`%/s` は直近の区間で1秒あたりに進んだ割合で、CPU 使用率ではない。
追加の前後で B1 の `%/s` を見比べる。
後から始めた A2 と A3 は進捗の累計が小さいため、バーの長さだけでは速度を比較できない。

最初は二つで順番を分け、追加後は四つで分ける。
一つの FIFO で同じスライスを渡すと、B1 の取り分はおよそ2分の1から4分の1へ減ると予想できる。
そのため、追加後の B1 の速度は追加前の約半分になる。

## 二つの列をどう使うか決める

前章で作った、PID の偶奇で二つの共有 DSQ に振り分ける状態から始める。
全員に同じ10ミリ秒のスライスを渡す設定を保ち、チームの判定と列の選び方を変える。
途中から参加した場合は、残したい変更を保存してから `make restore STEP=04` で二つの共有 DSQ がある状態に揃えられる。
この完成例は PID の偶奇で分類するので、そのままではチーム別にならない。

`enqueue` でチームごとに列へ入れた後、`dispatch` でどちらの列を選ぶかを考える。
B 用の列は一人のまま、A 用の列だけ三人になる。
その人数の差が、B 用の列へ回す順番を減らさないようにするには、どう選べばよいだろうか。

<details>
<summary>ヒント：プロセスの人数と、列に回す順番</summary>

一つの FIFO に A1、A2、A3、B1 が並ぶと、B1 の次の番までに A 側の三つが実行される。
チームごとの列があれば、「次はどのチームか」と「そのチームの誰か」を分けて決められる。
全員のスライスが同じなので、列を選ぶ回数からチーム全体の取り分を考えられる。

A のどれか一つだけを選び続けず、A 用の FIFO の先頭から取り出す。
片方の列が空の場合も、実行可能なタスクが残るもう一方から取り出せるようにする。

</details>

<details>
<summary>ヒント：名前の共通部分を使う</summary>

A 側の名前は、人数を変えてもすべて `team_a` で始まる。
前の課題で使った `p->comm` と `bpf_strncmp()` で、この先頭6文字を比較できる。
PID の偶奇は、今回のチーム分けとは関係がない。

</details>

## 同じ実験を lab で測る

```console
make team-race STEP=lab
```

今回は、A2 と A3 が加わっても B1 の `%/s` がほぼ同じままになることを目指す。
A1、A2、A3 のバーも、それぞれ進んでいるかを確かめる。
B1 だけを走らせ、A を止めてしまうと課題を満たさない。

追加後を約8秒観測すると、次の形式で平均速度と比率を表示する。
数値は表示形式の例である。

```text
before: A_total=5000.0 units/s B1=5000.0 units/s
after: A_total=5000.0 units/s B1=5000.0 units/s
B_after/B_before=1.00x  A_members=1->3
Measurement complete. Stopping all workers with unfinished work.
scheduler_state_after=disabled
```

`A_total` は A 全員が1秒あたりに終えた計算量の合計、`B1` は B1 が終えた計算量である。
`B_after/B_before` は追加後の B1 の速度を追加前の速度で割った値で、`1.00x` 付近なら速度を保てている。
`0.50x` 付近なら、追加後に約半分へ落ちている。
起動直後や人数が変わる途中を避けた区間から計算するため、画面の直近の `%/s` と多少異なることがある。
VM の実行状況でも揺れるので、何度か測って比べる。

<details>
<summary>観測後に読む：教材 VM での実測例</summary>

2026年9月9日に教材 VM の CPU 1 で測ったところ、一つの FIFO では `B_after/B_before=0.50x` だった。
二つの共有 DSQ を使う検証例では、A が3人で `1.00x`、5人で `0.99x`、7人で `1.00x` になった。
どの場合も A の全員の計算が進んでいた。
条件と出力は[実測記録](../measurements/2026-09-09/team-race.txt)に残している。

</details>

この実験は、全員の計算が完了する前に観測を終える。
バーが 100% でなくても正常で、起動した全プロセスを停止してスケジューラを解除する。
途中で `Ctrl+C` を押した場合も、この実験が起動したものを終了する。
末尾の `scheduler_state_after=disabled` で解除を確認する。

`other SCHED_EXT tasks` と表示された場合は、同じ CPU で動ける別の実験の負荷が残っている。
表示された PID をその実験の端末で終了するか、競合しない CPU を `RACE_CPU` で指定して測り直す。

## A をもっと増やしてみる

同じコードのまま、追加後の A の人数を変える。

```console
make team-race STEP=lab TEAM_A_MEMBERS=5
make team-race STEP=lab TEAM_A_MEMBERS=7
```

`TEAM_A_MEMBERS` は、追加後の A チーム全体の人数である。
5 を指定すると、最初の A1 に A2 から A5 までが加わる。
指定できる範囲は2人から7人で、B は常に B1 の一人である。

B1 の速度を保ち、A チーム全体へ渡す時間も同程度なら、A 一人あたりの速度は人数が多いほど下がる。
これは今回選んだ、チーム単位で時間を分ける規則の結果である。
一人あたりを同じにするか、チーム全体を同じにするかで、人数が変わったときの動きが異なる。
共有 DSQ を分けると、その配分を列の選び方で表現できる。

## make が準備していること

`make team-race` は指定したスケジューラと負荷プログラムを VM 内でビルドし、実験を開始する。
使う計算処理は前の課題と同じ `race-worker` である。
各プロセスに約30 CPU 秒を目安にした同じ仕事量を与え、観測中に仕事を終えないようにしている。

A1 と B1 が計算を始めてから約5秒後に追加の A を起動し、全員が計算を始めてから約8秒観測する。
各区間の最初の1秒を平均速度の計算から除く。
表示のために計算プロセスを sleep させることはなく、観測用プロセスが共有メモリの完了数を読み取る。
観測が終われば、残りの仕事量にかかわらず全員を停止する。
処理を追う場合は `scripts/guest/team_race_experiment.py` と `tools/workload/src/race.rs` を読む。

> A が3人になったとき、`B_after/B_before` は［　　　］だった。<br>
> A が［　　　］人になったとき、比率は［　　　］だった。<br>
> A の各プロセスは［　　　］のように進んでいた。

人数を変えたときにも同じ規則で狙った速度を保てれば、最初の四つの PID にだけ合わせた変更ではないことを確かめられる。
