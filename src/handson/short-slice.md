# スライスを短くする

2 秒のスライスでは、後から wakeup した periodic が hog の実行を長く待ちうる。
スライスを 10 ミリ秒へ縮めれば、もっと早く順番が回ってくるだろうか。
共有 DSQ と三つのタスクはそのままにして、スライスだけを変更する。

## 実行前に予想する

最大遅延とコンテキストスイッチ数は、それぞれどちらに動くか。
前章で書いたキューの並びを使い、待ち時間のモデルも計算する。
一つの値が改善したとき、もう一つも同じ向きに動くとは限らない。

## lab のスライスを 10 ミリ秒にする

`lab/src/bpf/main.bpf.c` の定数を変更する。
途中から始める場合は、必要な変更を保存してから `make restore STEP=03` で長いスライスの状態へ戻せる。

```c
const volatile u64 slice_ns = 10000000ULL;  /* 10 milliseconds */
```

ホスト側で同じ 15 標本の実験を行い、ログを保存する。

```console
mkdir -p target/measurements
make bench CASE=step STEP=lab 2>&1 | tee target/measurements/short.log
```

完成状態を使う場合は `STEP=04` を指定できる。
自分の変更を測るときは `STEP=lab` を使う。
前章の結果と比べ、最大遅延が下がったか、deadline miss が減ったか、切り替えが増えたかを調べる。

## 結果を記録する

三つのログから次の値を転記する。
最大遅延と deadline miss は periodic の集計、切り替え回数は `perf stat` の出力を見る。

| 条件 | 最大遅延（ms） | deadline miss（標本数 / 15） | context switches（回） |
|---|---:|---:|---:|
| fair class |  |  |  |
| 2 秒スライス |  |  |  |
| 10 ミリ秒スライス |  |  |  |

各ログには実行日とホストの負荷状況も添えておく。
再測定するときは同じ三条件を繰り返し、一回だけの外れ値と、繰り返し現れる傾向を区別する。

## 一回の実測との比較

前章と同じ環境で続けて測った結果は、次のようになった。
[短いスライスの全標本と測定条件](../measurements/2026-09-06/short.txt)を確認できる。

| 条件 | 最大遅延（ms） | deadline miss | context switches（回） |
|---|---:|---:|---:|
| fair class | 1.686 | 0 / 15 | 5,167 |
| 2 秒スライス | 3,468.367 | 15 / 15 | 177 |
| 10 ミリ秒スライス | 21.272 | 0 / 15 | 1,546 |

10 ミリ秒では、2 秒に比べて最大遅延が下がり、切り替え回数が増えた。
一方、fair class の切り替え回数はこの二条件より多い。
キューの方針まで異なる fair class を含めて「回数が少ないほどよい」と順位を付ける表ではない。
自分のログでも、まず同じ FIFO の長短二条件を比べる。

## 切り替え回数から分かること

同じ hog A と hog B が、2 秒ごとに交互に走る場合と、10 ミリ秒ごとに走る場合を考える。
後者は periodic を早く選び直せる一方、hog 同士を切り替える機会も増える。
前章のモデルで最大 2 スライス分だった待ちは、10 ミリ秒なら約 20 ミリ秒になる。
この値も runnable 後の待ちを単純化したモデルであり、`late_ms` の上限ではない。

同じ 60 ミリ秒を上下に並べると、CPU を渡す機会の違いが見える。
両方とも hog A がスライスを開始した直後から描き、hog B はすでに待ち、periodic は 5 ミリ秒で runnable になると仮定する。

2 秒スライスの行は、hog A の実行途中で表示範囲が終わっている。
10 ミリ秒の行では、periodic は 15 ミリ秒待って CPU を得る。
periodic の実行時間を説明用に 2 ミリ秒と置き、割り込みと切り替え時間は省略した模式図である。
実測値の表とは区別して読む。

実測の遅延が減り、切り替え回数が増えていれば、この説明と整合する。
逆の結果やほとんど差がない結果なら、まず [CPU 固定、タスク数、適用中のスケジューラ](../appendix/troubleshooting.md#実験で遅延が見えない)を確認する。
測定が hog の終了後まで延びていないか、ログ末尾だけ遅れが小さくなっていないかも見る。

ただし、切り替え回数の増加だけでは、切り替えコストが何ミリ秒増えたかは分からない。
別のタスクへ移るとスケジューラの処理が必要になり、キャッシュの再利用にも影響しうるが、この実験はその内訳を測っていない。
CPU-bound な仕事の throughput が下がったかを判断するには、同じ時間で完了した仕事量などを別に測る必要がある。

## 別のスライスを試す

10 ミリ秒から 50 ミリ秒へ変更したら、待ち時間と切り替え回数はどう変わるだろうか。
まずモデルで予想し、`slice_ns` を自分で変更して `STEP=lab` で測定する。
結果は別のログに保存し、実験後は 10 ミリ秒へ戻しておく。

<details>
<summary>予想の例</summary>

50 ミリ秒は `50000000ULL` ナノ秒である。
二つの hog が先行するモデルなら、runnable 後の待ちは最大約 100 ミリ秒になる。
10 ミリ秒より待ちが長くなりうる一方、hog 同士の切り替えは減ると予想できる。
許容値も 100 ミリ秒だが、`late_ms` はモデル外の遅れを含むため、deadline miss が必ずゼロになるとは言えない。

</details>

スライスを短くして得たいのは、周期タスクを早く再開させる機会である。
その機会を増やすために、どれだけ頻繁な切り替えを許すか。
自分の表にある遅延と切り替え回数を使って、今回の負荷にどの設定を選ぶか説明してみる。
