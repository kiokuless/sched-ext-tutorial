# スライスを短くする

前章では、2秒のスライスが周期タスクを数秒単位で待たせる様子を観測した。
周期タスクを早く再開させる最も単純な方法は、CPU-bound タスクから頻繁に CPU を取り上げることだ。
スライスを10ミリ秒へ縮める。

ここには、一見すると分かりやすい最適化の方向がある。
2秒より10ミリ秒の方が周期タスクを早く選び直せるなら、スライスは短ければ短いほど良さそうに見える。
もし応答性だけを目的にするなら、その考えはかなり自然である。
この章では、まずその仮説の前半（短くすると遅延が減るか）を確かめる。
同時に、改善を得るために何を支払っているのかも測る。

ここで変更するのは、キューの構造でも CPU の選び方でもない。
前章と同じ FIFO を使ったまま、CPU を保持できる時間だけを短くする。
一度に一つの条件だけを変えることで、観測値の差をタイムスライスへ帰属させやすくする。
scheduler の実験では、この「他の条件を固定する」ことがコードそのものと同じくらい重要である。

## 予想

ベンチマークを回す前に、二つの観測値の向きを予想しておく。
最大遅延はどちらに動くか。
context switches はどちらに動くか。
前章までの仕組みから、両方の向きと理由を紙の上で説明できるはずである。

## 10ミリ秒のスライス

```console
make restore STEP=04
```

この checkpoint も、コードの変更は定数一行だけである。
キューの作り方も、dispatch の書き方も、前章と同じである。

```c
const volatile u64 slice_ns = 10000000ULL;  /* 10 milliseconds */
```

同じ15秒の実験を繰り返す。

```console
make bench CASE=step STEP=04
```

出力形式は前章と同じである。
実行前に書いた予想と照らし合わせ、まず方向を見る。
2秒スライスと比べて最大遅延は下がったか、deadline miss は減ったか、context switch は増えたか。
具体的な値は環境に依存するので、ここでは「何ミリ秒なら成功」といった固定値を置かない。

## 結果を記録する

長いスライスの結果と比べ、次の値を記録する。

| 条件 | 最大遅延 | deadline miss | context switches |
|---|---:|---:|---:|
| fair class |  |  |  |
| 2秒スライス |  |  |  |

## トレードオフを読む

最大遅延が減っても、コンテキストスイッチ数は増えるはずだ。
二つの CPU hog が短いスライスで交互に実行されるため、2秒スライスより多くの context switch が観測される。
実測がそうならなかった場合は、CPU hog が二つ動いているか、CPU 固定と scheduler の状態を確認する。

遅延の減少と切り替えの増加は、同じ一行の変更から同時に生じた。
短いスライスが常に優れているわけではない。
選び直す機会を増やした代わりに、切り替えの処理とキャッシュ状態の損失を増やしている。
スライスの長さは、応答性と切り替えコストの間の設計判断である。
scheduler に何を優先させるかで、この値の置きどころが変わる。

では、10ミリ秒で遅延が改善するなら、1ミリ秒や100マイクロ秒まで短くすればさらに良いのだろうか。
応答性だけを見れば、CPU を選び直す機会はさらに増える。
しかし、切り替えのたびに scheduler の処理が必要になり、別のタスクへ移ればキャッシュや TLB の局所性も失いやすくなる。
極端に短いスライスでは、仕事そのものより切り替えのために使う割合を無視できなくなる。

逆に、スライスを長くすれば CPU-bound workload の実行をまとめやすいが、今回の周期タスクのような latency-sensitive workload は待たされる。
現実の scheduler が単純に「最短のスライス」を選ばないのは、このためである。
一つの数値を最小化するだけでは、scheduler の良し悪しは決まらない。
どの workload にどの性質を与えたいかを決め、その結果として現れるトレードオフを観測する必要がある。
