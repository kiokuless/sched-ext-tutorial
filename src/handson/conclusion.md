# 次の方針を選ぶ

スライスを変更し、自分の待ち行列からタスクを渡すスケジューラを作った。
手元には、三つの条件で観察した sleep の時間と、PID の偶奇で列を分けたときの CPU 時間の配分がある。
さらに、A と B の進み方を変える課題で、自分の規則と実際の計算速度を照合した。
チームごとの共有 DSQ を使う課題では、人数が増えても B の速さを保てるかを測った。
最後は、その数字から次に試す方針を一つ選ぶ。

## 結果に数値と理由を添える

[1秒後に戻れないタスク](./long-slice.md#スライスを短くしてみる)で残した出力を見返す。
2 秒と 10 ミリ秒の条件で、表示の間隔を比べてみる。

> スライスを 2 秒から 10 ミリ秒へ変えた。<br>
> 表示の間隔は［　　　］秒から［　　　］秒へ変わった。

戻るまでの時間が短くなった場合は、次の一文を続けられる。

> 計算タスクから早く交代できるため、sleep の順番待ちが短くなるという説明と整合する。

変わらなかった場合や増えた場合は、そのまま記録する。

> 今回の測定では、スライスを短くすると待ちが減るという予想を確認できなかった。

表示の間隔には、1秒の sleep と CPU 待ちのほかに、出力処理などの時間も含まれるので、どちらの場合も原因のすべてを確定したことにはならない。
変えたものと見えた結果を分けて書けば、別の条件で再測定するときにも比較できる。

## 何を優先するか

同じ二つの設定でも、使い道によって選ぶ理由が変わる。
眠っていたタスクの応答を早めたいなら、表示の間隔が判断の材料になる。

一方、切り替えを減らすことを試したいなら、長めのスライスを候補にできる。
ただし回数が少ないだけで、計算が速く終わるとは限らない。
同じ時間で完了する仕事量を **throughput** と呼ぶ。
前章の進捗バーも、実際に終えた仕事量から作った。
切り替え回数が変わったときは、進捗速度も変わったかを別に確かめる。

| 優先したいこと | 手元で見る値 | 追加で確かめること |
|---|---|---|
| 眠っていたタスクの応答 | 表示の間隔 | 同じ条件で遅れが繰り返し減るか |
| 切り替え回数の削減 | 別途 context switches を測る | sleep の遅れをどこまで許容するか |
| 計算の throughput | A と B の進捗速度 | 片方の速度と、二つを合わせた仕事量の両方 |
| チームごとの取り分 | A の追加前後の B の進捗速度 | 人数を変えても速度を保ち、A の全員にも順番が回るか |

「最もよいスライス」を一つ決める前に、今回どの値を改善したいかを選べばよい。
自分の記録がその判断に使えることも、コードを変更して測った成果である。

## 長い計算と早い応答を両立したい

計算タスクには長めのスライスを渡したいが、入力への応答は早く動かしたい。
全タスクに同じスライスを渡す今のコードでは、この二つを別々に調整できない。

次に試す方向としては、「全員のスライスをさらに短くする」と「応答タスクを区別して扱う」がある。
計算タスクのスライスを保ちたいなら、後者が候補になる。

たとえば、タスクの種類があらかじめ分かるなら、`enqueue` の偶奇による分類を、応答用と計算用の分類に変えられる。
二つの列を交互に選んでいた `dispatch` も、応答用が空でなければそこから、空なら計算用から取り出す処理へ変える。
偶数側の三つと奇数側の一つを動かした実験では、分類と列の選び方が、各プロセスの CPU 時間へ影響した。
その二つの規則を、処理の目的に合わせて変える形である。

それでも、今 CPU 上で走っている計算タスクは、待ち行列の順序を変えただけでは直ちに止まらない。
スライスが尽きる前に CPU を譲らせる仕組みを **プリエンプション** と呼ぶ。
早く応答する方針には、待っているタスクの選び方と、実行中のタスクへいつ交代を求めるかの両方が関わる。
応答が来続けても計算を進めるために、計算用の DSQ にも順番を回す規則が必要になる。

この続きは、[`sched_ext_ops` の使いどころ](../advanced/ops.md)で判断を入れるタイミングから考えられる。
一からスケジューラ全体を考案する前に、今の `enqueue` と `dispatch` のどこを変えそうか、見当を付けられればよい。

## 関心のある方向へ進む

発展編は、次に変えたいものや確かめたいことから選べる。

| 次の関心 | 読む章 |
|---|---|
| shell やコンパイラにも自作の方針を適用したい | [VM 全体へ広げる](../advanced/system-wide.md) |
| タスクを進められないときの復帰を確かめたい | [壊して、戻る](../advanced/watchdog.md) |
| タスクを選ぶ判断を増やしたい | [`sched_ext_ops` の使いどころ](../advanced/ops.md) |
| CPU を移る回数を減らしたい | [CPU ごとの DSQ](../advanced/per-cpu-dsq.md) |
| まれに大きく遅れる理由を調べたい | [tail latency の測り方](../advanced/tail-latency.md) |
| 複雑な方針を Rust で書きたい | [Rust で方針を書く](../advanced/rustland.md) |
| VM の外で性能を評価したい | [実機で評価する](../advanced/bare-metal.md) |

実際のコードへ広げるなら、由来となった [scx_simple](https://github.com/gregkh/linux/blob/v6.18/tools/sched_ext/scx_simple.bpf.c) の `enqueue` や `dispatch` を、自分が編集した関数と並べて読める。
本編以外の経路は、Linux の [Scheduling Cycle](https://docs.kernel.org/7.0/scheduler/sched-ext.html#scheduling-cycle) で確認できる。

冒頭の `sleep(1)` が戻る時刻には、CPU を使う順番も影響していた。
その順番と時間を決めるコードに手を入れ、起動ログと測定値で変更を確かめた。
次の実験でも、まず一つ変える場所を選び、その変更で動きそうな値を一つ決めるところから始められる。
