# 次の方針を選ぶ

スライスの長さは sleep の再開待ちに、待ち行列の分け方はプロセスやチームが受け取る CPU 時間に影響する。
本編では、それぞれの条件を変えて動かし、結果を記録した。

手元には、三つの条件での sleep の時間、PID の偶奇で分けたときの配分、A と B の計算速度、人数を増やす前後の B の速度がある。
これらを使い、応答の早さや計算の進み方のうち、次に改善したいものを選ぶ。

## 結果に数値と理由を添える

測定結果は、変更した条件と観測した値を対応させて記録する。
たとえば、[1秒後に戻れないタスク](long-slice.md#スライスを短くしてみる)で残した 2 秒と 10 ミリ秒の出力なら、次のように書ける。

> スライスを 2 秒から 10 ミリ秒へ変えた。
> <br>
> 表示の間隔は［　　　］秒から［　　　］秒へ変わった。

戻るまでの時間が短くなった場合は、結果を説明する一文を添える。

> 計算タスクから早く交代できるため、sleep の順番待ちが短くなるという説明と整合する。

変わらなかった場合や増えた場合も、そのまま記録する。

> 今回の測定では、スライスを短くすると待ちが減るという予想を確認できなかった。

表示間隔には、1 秒の sleep と CPU 待ちだけでなく、出力処理などの時間も含まれる。
そのため、どちらの結果でも原因のすべてを確定したことにはならない。
変更した条件、観測した値、その値を説明する考え方を分けて書けば、別の条件で再測定するときにも比較できる。

## 何を優先するか

眠っていたタスクの応答を早めたいなら、sleep の表示間隔が判断の材料になる。
一方、切り替え回数を減らしたいなら長めのスライスが候補になるが、切り替えが少ないだけで計算が速く終わるとは限らない。

計算の速さを評価するには、同じ時間で完了した仕事量である **throughput** を測る。
進捗バーも実際に終えた仕事量から作っているので、切り替え回数とは別に、進捗速度が変わったかを確かめる。

| 優先したいこと | 手元で見る値 | 追加で確かめること |
|---|---|---|
| 眠っていたタスクの応答 | 表示の間隔 | 同じ条件で遅れが繰り返し減るか |
| 切り替え回数の削減 | 別途 context switches を測る | sleep の遅れをどこまで許容するか |
| 計算の throughput | A と B の進捗速度 | 片方の速度と、二つを合わせた仕事量の両方 |
| チームごとの取り分 | A の追加前後の B の進捗速度 | 人数を変えても速度を保ち、A の全員にも順番が回るか |

## 長い計算と早い応答を両立したい

計算タスクには長めのスライスを割り当て、入力への応答は早く動かしたい場合を考える。
全タスクに同じスライスを渡す今のコードでは、二つを別々に調整できない。
全員のスライスを短くすれば、計算タスクのスライスも短くなる。
計算用の長さを保つには、応答用と計算用のタスクを区別する方法が候補になる。

タスクの種類があらかじめ分かるなら、`enqueue` の偶奇による分類を、応答用と計算用に変えられる。
`dispatch` では、応答用の列が空でなければそこから、空なら計算用から取り出す。
偶数側の三つと奇数側の一つを動かした実験と同じく、分類と列の選び方で配分を調整する。
ただし、応答が来続けても計算を進めるためには、計算用の DSQ にも順番を回す規則が必要である。

待ち行列の順序を変えるだけでは、今 CPU 上で走っている計算タスクは直ちに止まらない。
スライスが尽きる前に CPU を譲らせる仕組みを **プリエンプション** と呼ぶ。
早く応答する方針には、待っているタスクの選び方と、実行中のタスクへ交代を求めるタイミングの両方が関わる。
後者は、[`sched_ext_ops` の使いどころ](../advanced/ops.md)で検討する。
