# 観測結果を説明する

最初に見た周期タスクは、タイマー満了だけでは実行を再開できなかった。
同じ CPU で2秒スライスを使うタスクが走っていたため、runnable になったあとも dispatch を待った。

スライスを10ミリ秒へ縮めると、scheduler は CPU を選び直す機会を増やした。
周期タスクの遅延が減り、コンテキストスイッチ数が増えたなら、その二つは同じ変更から生じている。

実験記録へ次の三点を書く。

1. 変更した値または callback
2. 変化した観測値
3. 変化が起きた理由

たとえば、「短いスライスのほうが速かった」だけでは理由が抜けている。
「スライスを2秒から10ミリ秒へ変更したため、CPU-bound タスクを再 enqueue する間隔が短くなり、周期タスクが dispatch されるまでの最大遅延が減った」と書けば、変更と観測がつながる。

一方、コンテキストスイッチの増加は、この改善が無料ではないことを示す。
別の方針なら、長いスライスを保ちながら起床タスクだけをプリエンプトできるかもしれない。
