# 観測結果を説明する

はじめに見た周期タスクは、タイマー満了だけでは実行を再開できなかった。
同じ CPU で長いスライスを持つ CPU-bound タスクが走っていると、周期タスクは runnable になったあとも FIFO の中で dispatch を待つ。
スライスを2秒から10ミリ秒へ縮めると、CPU を選び直す機会が増える。
この実験条件では、その変更が周期タスクの遅延と context switch の両方へ影響する。

本編で比べた三条件を、数値ではなく仕組みで整理すると次のようになる。

| 条件 | 変えたもの | 遅延について見ること | context switch について見ること |
| --- | --- | --- | --- |
| fair class | 自作 `sched_ext` を使わない基準条件 | 比較の基準 | 比較の基準 |
| 2秒スライス | FIFO の slice を長くする | runnable 後の待ちが大きくなりうる | 選び直す機会は少ない |
| 10ミリ秒スライス | FIFO の slice を短くする | 2秒条件より待ちが減るか | 2秒条件より増えるか |

ここで大切なのは、表の右側を暗記することではない。
条件を一つだけ変え、観測値が動いた理由を scheduling path に戻って説明することである。
絶対値は VM やホスト負荷に依存するが、同じ環境で条件を固定して比較すれば、どの設計変更がどの変化に関係したのかを調べられる。

## 変更、観測、理由をつなぐ

実験の締めくくりとして、観測したことを自分の言葉で説明にまとめる。
実験記録には次の三点を書く。

- 何を変更したか
- どの観測値がどう変わったか
- なぜその変化が起きたと考えられるか

「短いスライスのほうが速かった」だけでは、何を測ったのかも、なぜ変化したのかも分からない。

たとえば次のように書けば、変更と観測を scheduling の仕組みで結び付けられる。

> スライスを2秒から10ミリ秒へ変更した。
> CPU-bound タスクを選び直す機会が増えたため、FIFO で後から runnable になった周期タスクが dispatch を待つ時間は短くなった。
> 一方、二つの CPU-bound タスクを切り替える機会も増えたため、context switch は増加した。

自分の実測がこの通りでなければ、文章を実測へ合わせて書き直す。
教材の期待値へ数字を合わせるのではなく、観測した事実を説明するのが目的である。

## 次の scheduler を設計する

CPU-bound タスクのスライスは必要以上に短くしたくない。
それでも、周期的に起きる latency-sensitive なタスクはなるべく早く実行したい。

単に `slice_ns` をさらに短くする以外に、何ができるだろうか。
まだコードを書く必要はない。
次の三点を考えてみる。

- scheduler は、どの判断点で「優先して動かしたいタスクが起きた」と知れるか
- そのとき、すでに CPU 上で動いているタスクをどう扱う必要があるか
- 一つの FIFO だけで表現できるか、それとも追加の状態や別のキューが必要か

この問いに答えようとすると、本編で使わなかった callback が必要になる理由が見えてくる。
API を一覧から選ぶのではなく、「実現したい scheduling policy には、どの判断点が足りないか」から逆算する。
そのための材料は、発展編の [`sched_ext_ops` の使いどころ](../advanced/ops.md)にある。

## 次の一歩

本編の知識を外の実装へつなぐなら、次の順で読むと迷いにくい。

1. Linux の `sched_ext` 文書で scheduling cycle と callback の一覧を見る
2. scx リポジトリの `scx_simple` を、本編の scheduler と並べて読む
3. 発展編から、興味のある設計軸（callback、CPU ごとの DSQ、tail latency、ユーザ空間 scheduler、実機評価）を選ぶ
