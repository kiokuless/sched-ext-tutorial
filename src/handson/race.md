# A を B の2倍の速さで進める

同じ計算をする二つのプロセスを、一つの CPU で動かす。
名前は `race_a` と `race_b` で、以降は A と B と呼ぶ。
同じスライスを同じ回数だけ割り当てれば、二つの進捗バーはほぼ並んで進む。
計算内容を変えずに A だけを速く進めるには、CPU 時間の配分をどう変えればよいだろうか。

## 今回の課題

> A と B が両方動いている間、A を B の約2倍の速さで進めるスケジューラを作る。<br>
> 計算プログラムと仕事量は変えず、スケジューラを変更する。<br>
> A が終わった後も B を最後まで動かし、B の進む速さがどう変わるかを観察する。

「2倍」は、両方が動いている間に終える計算量の比率を指す。
A が 40% まで進んだときに B が 20% 付近にいる、という動きが目標である。
A が終了すると B が使える CPU 時間も変わるため、完了までの所要時間の比率とは区別する。

## 変更前の二つを動かす

Mac 側のリポジトリ直下で実行する。
前の実験のスケジューラと負荷プロセスは、動かした端末で先に終了しておく。

```console
make race STEP=03
```

このコマンドは完成例をビルドして partial mode で起動し、A と B を CPU 0 に揃えて動かす。
`STEP=03` は、全員を一つのグローバル DSQ に入れ、同じ10ミリ秒のスライスを渡す完成例である。
A と B は、それぞれ同じ有限の仕事量を終えたら終了する。
約1秒ごとに、名前、PID、実行を許可した CPU、進捗バー、直近の進捗速度が表示される。

次は表示形式の例で、PID と数値は起動するたびに変わる。

```text
ready: name=race_a PID=12340 CPU=0
ready: name=race_b PID=12341 CPU=0
Starting both workers. Ctrl+C stops this experiment.
elapsed=  6.0s  A / B
race_a PID=12340   CPU=0 [######------------------]  25.0%    4.2%/s
race_b PID=12341   CPU=0 [######------------------]  25.0%    4.2%/s
```

`25.0%` は全仕事量のうち終わった割合、`4.2%/s` は直近の区間で1秒あたりに進んだ割合である。
CPU 使用率の表示ではない。
例えば A が 8%/s、B が 4%/s なら、その区間では A が約2倍の速さで計算を進めている。

変更前は、二つのバーがほぼ並んで進むことを確かめる。
両方が終わると速度の比較が表示され、スケジューラも解除される。
途中で終える場合は `Ctrl+C` を押す。
このコマンドが起動した二つのプロセスとスケジューラを終了する。

## 自分の規則を入れる

編集先は `lab/src/bpf/main.bpf.c` である。
前章で読んだ、一つのグローバル DSQ を使う状態から始める。
途中から参加した場合は、残したい変更を保存してから `make restore STEP=03` で揃える。

全員に同じ `slice_ns` を使う今の実装から、A と B を区別して CPU 時間を割り当てる実装へ変える。
区別に使う情報と、各タスクに割り当てる値を考える。

<details>
<summary>ヒント：回数と一回の長さ</summary>

同じ長さのスライスを同じ回数だけ渡すと、A と B が受け取る CPU 時間も近くなる。
実行する順番を保ったまま、一回の長さを変えるとどうなるだろうか。

`scx_bpf_dsq_insert()` の第3引数で、タスクごとのスライスを指定できる。
今は全員に `slice_ns` を使っているので、この引数をタスクに応じて選ぶ。
単位はナノ秒なので、10 ミリ秒は `10000000ULL` である。

</details>

<details>
<summary>ヒント：race_a を名前で見分ける</summary>

今回の負荷プログラムは、起動時に自身の名前を `race_a` または `race_b` に設定している。[^race-name]
`enqueue` が受け取るタスクの `p->comm` からこの名前を読めば、再実行で PID が変わっても A と B を区別できる。

例えば、`oreore_enqueue` の中で次のように判定できる。

```c
bool is_a = bpf_strncmp(p->comm, sizeof(p->comm), "race_a") == 0;
```

`bpf_strncmp()` は、文字列が一致すると 0 を返す。
第2引数には読み取る領域の大きさ、第3引数には比較する文字列を渡す。[^race-compare]
この `is_a` を使って、タスクに渡すスライスを選べる。

`comm` は短いスレッド名で、実行ファイルのパスやコマンドライン全体ではない。
A と B は単一スレッドなので、ここではプロセスの名前として扱える。

</details>

## 変更したコードでもう一度走らせる

変更を保存してから、同じ実験を lab で行う。

```console
make race STEP=lab
```

実験のたびに lab をビルドし直し、新しい A と B を起動する。
実行中のコードを差し替える操作は必要ない。
まだ A と B が両方動いているうちに、それぞれの `%/s` とバーの進み方を見る。

二つが動いている間の速度が A:B = 2:1 に近ければ、A が先に `done` になる。
その前後で B の `%/s` を比べ、A が使っていた CPU 時間を残った B が使えるかを確かめる。

最後の出力では、次の二つを読む。

| 出力 | 読み取れること |
|---|---|
| `while_both` の `A/B` | 両方が動いていた区間の、A の速度 ÷ B の速度 |
| `after_A` の `B_speedup` | A の終了後の B の速度 ÷ 両方が動いていた区間の B の速度 |

`A/B=2.00x` に近い値なら、同時に動いていた区間で A が約2倍の速さで進んだことになる。
起動直後の偏りや終了間際を避け、複数の観測値から計算した平均である。
VM の実行状況などで値は揺れるので、一回の表示だけで判断せず、再実行して比べる。

`after_A: insufficient measurement time` は、A だけが終わった区間を十分に測れなかったことを示す。
例えば A と B がほぼ同時に終われば、この比較はできない。
速度差を作れた場合は、A の終了後も B が動く区間ができる。

末尾の `scheduler_state_after=disabled` で解除を確認する。
`other SCHED_EXT tasks` と表示されて中止した場合は、同じ CPU に前の実験のタスクが残っている。
表示された PID の負荷を、その実験の端末で終了してから測り直す。

<details>
<summary>観測後に読む：B は何倍に速くなるか</summary>

二つが受け取る CPU 時間を 2:1 に分けると、B の取り分は全体の3分の1になる。
A の終了後、B がその全体を使えるなら、B の速度は終了前の約3倍になる。
例えば A が 8%/s、B が 4%/s だったなら、残った B が約12%/s へ上がるという予想である。

B のスライスを伸ばさなくても、競争相手がいなくなれば、次の順番も B に回せる。

</details>

<details>
<summary>観測後に読む：教材 VM での実測例</summary>

2026年9月9日に、教材 VM の CPU 1 で、一つのグローバル DSQ を使う検証例を動かした。
名前が `race_a` のときだけスライスを2倍にすると、`A/B=2.00x`、`B_speedup=2.99x` になった。
条件と出力は[実測記録](../measurements/2026-09-09/race-global.txt)に残している。

## make が準備していること

進捗バーの元は、負荷プログラムが実際に終えた計算の回数である。
同じ演算を繰り返すひとかたまりを `unit` として数え、A と B がそれぞれ同じ数の unit を終えたら終了する。
一定秒数が過ぎたら終了する `cpu-hog` とは、終了条件が異なる。

`make race` は VM 内で次の準備と観測を行う。

1. 負荷プログラムと指定したスケジューラをビルドする。
2. 短い計算で処理速度を見積もり、一つあたり約12 CPU 秒を目安に、今回の仕事量を決める。
3. スケジューラを partial mode で起動する。
4. A と B の名前と CPU affinity を設定し、両方の準備ができてから計算を始める。
5. 完了した unit 数を定期的に読み、進捗と速度を表示する。
6. 二つが終わったら速度を比較し、スケジューラを解除する。

約12 CPU 秒は仕事量を決めるための目安であり、12秒後に止める指定ではない。
各実行内で A と B の仕事量を同じにするため、マシンの速さが異なっても比較できる。
計算中の A と B は、表示のたびに sleep せず、共有メモリ上の完了数を更新する。
表示は別のプロセスが担当する。
処理を追う場合は `scripts/guest/race_experiment.py` と `tools/workload/src/race.rs` を読む。

## 自分の結果を残す

使った規則と、観測した二つの比率を記録する。

> ［　　　］を見て A と B を区別し、［　　　］を変更した。<br>
> 両方が動いている間の `A/B` は［　　　］だった。<br>
> A の終了後の `B_speedup` は［　　　］だった。

予想と違った場合は、違った値をそのまま残す。
例えば A だけに渡すつもりのスライスが B にも渡っていれば、二つの進み方は近いままになる。
どの条件で、どの値を渡したかを読み直すと、修正する場所を絞れる。

[^race-name]: Linux の [PR_SET_NAME](https://man7.org/linux/man-pages/man2/PR_SET_NAME.2const.html) は、呼び出したスレッドの名前を設定する。
    終端の null 文字を含めた上限は16バイトである。
[^race-compare]: Linux 7.0 の [BPF helper の定義](https://github.com/torvalds/linux/blob/v7.0/include/uapi/linux/bpf.h)に、`bpf_strncmp()` の引数と戻り値が記載されている。
