# 1秒後に戻れないタスク

`sleep(1)` を呼んだタスクは、1 秒後に実行を再開できるのだろうか。
タイマーが満了すれば再び実行可能になるが、その瞬間の CPU が予約されているわけではない。
同じ CPU で別のタスクが走り続けていれば、起きたタスクも待つことになる。

前章で作った共有 DSQ を使い、スライスを 2 秒に伸ばしてみる。
眠らずに計算するタスクが長く CPU を使う条件を作ると、周期的に起きるタスクの遅れを数秒単位で観察しやすくなる。

## 実験の条件

二つの **CPU-bound タスク**（主に CPU 計算を続けるタスク）と、1 秒間隔の予定時刻に処理を再開する周期タスクを CPU 0 に固定する。
負荷生成器の `cpu-hog` を二つ、`periodic` を一つ使う。
以下ではそれぞれを hog A、hog B、periodic と呼ぶ。

`taskset -c 0` は、タスクが実行できる CPU を CPU 0 だけに制限する。
この制約を **CPU affinity** と呼び、空いている別の CPU に逃げず、同じ CPU を奪い合う条件を作れる。
`taskset` 自体はスケジューリング方針を変更しない。

hog が一つだけなら、periodic が眠っている間にスライスが尽きても、同じ hog が続けて走れる。
hog を二つ置くと、スライスの切れ目で交互に実行する相手ができる。
遅れに加えて、タスクを切り替えた回数である **コンテキストスイッチ数** も比較するための条件である。

CPU affinity、タスク数、キュー構造を揃え、スライスだけを変える。
比較対象として、自作スケジューラを使わず、fair class で同じ負荷を動かした結果も取る。

## 実行前に予想する

hog A と hog B が走り続ける間に periodic が runnable になったとする。
ほかのタスクの割り込みを無視した FIFO のモデルでは、periodic は先に何を待つだろうか。
2 秒スライスを最大で何回分待つか、キューの並びを書いて予想する。

## lab のスライスを 2 秒にする

前章で編集した `lab/src/bpf/main.bpf.c` を開く。
途中から始める場合は、必要な変更を保存してから `make restore STEP=02` で共有 DSQ の完成状態へ戻せる。
ファイル先頭の `slice_ns` を、次の値へ変更する。

```c
const volatile u64 slice_ns = 2000000000ULL;  /* 2 seconds */
```

単位はナノ秒なので、2 秒は `2,000,000,000` である。
この値は `scx_bpf_dsq_insert()` の第3引数として、タスクを DSQ に入れるときに渡される。
`dispatch` の処理やキューの順序は変更しない。

## ベンチマークを実行する

前章の `make run` が動いていれば `Ctrl+C` で終了し、VM 内の `/sys/kernel/sched_ext/state` が `disabled` になったことを確認する。
`CASE=fair` は自作スケジューラをロードしないが、すでに動いているものを自動で外すわけではない。
比較を始める前に状態を揃える。

ホスト側のリポジトリで、まず fair class の測定を行う。
`tee` で保存したログは、次章の比較にも使う。

```console
mkdir -p target/measurements
make bench CASE=fair 2>&1 | tee target/measurements/fair.log
```

続いて、編集した lab を測定する。

```console
make bench CASE=step STEP=lab 2>&1 | tee target/measurements/long.log
```

`STEP=lab` は手元で編集したコードを使う。
完成状態を直接試す場合は `STEP=03` を指定できるが、その結果に lab の変更は反映されない。

`make bench` はビルド、ロード、有効化の確認、負荷生成、停止をまとめて行う。
別の端末で `make run` を起動しておく必要はない。
二つの hog をそれぞれ約 20 秒間動かし、periodic は 1 秒間隔の予定時刻に対して 15 標本を記録する。
実際の終了時刻はスケジューリングによる遅れで延びうる。
`CASE=step` では三つの負荷生成器が `--sched-ext` を指定し、partial mode の対象へ入る。

## 測っている遅れ

periodic の `late_ms` は、**予定時刻から処理を再開するまでの遅れ**をミリ秒で表す。
次の三つの時刻を区別する必要がある。

- **予定時刻**：負荷生成器が定めた、処理を再開したい時刻
- **runnable になった時刻**：眠っていたタスクが実行可能になった時刻
- **処理を再開した時刻**：負荷生成器が `sleep` から戻って時刻を読んだ時点

負荷生成器は予定時刻と処理再開時刻を記録するが、runnable になった時刻は取得していない。
そのため `late_ms` には、runnable になるまでの遅れと、CPU を待つ時間などが含まれる。
VM 自体がホスト側で実行を待たされる影響も混ざる。
この値だけから「遅れのすべてが dispatch 待ちだった」とは判断できない。

予定時刻は、前回の処理再開から 1 秒後に置き直さず、毎回 1 秒ずつ進める。
大きく遅れたときは次の予定時刻も過ぎているため、ほとんど眠らずに次の標本を記録する場合がある。
15 標本は独立した 15 回の起床待ちを意味しない。

出力の `deadline_missed` は、`late_ms` が 100 ミリ秒の許容を超えたときに `true` になる。
これを、この実験での **deadline miss** と呼ぶ。
最後の `max_late_ms` は最大遅延、`deadline_misses` は許容を超えた標本数である。
15 標本から p95 や p99 を安定して評価することはできないので、本編では個々の遅延、最大遅延、deadline miss 数を比べる。

`perf stat` の `context-switches` は、periodic の実行期間中に CPU 0 で発生した切り替えを数える。
三つの実験タスク以外の切り替えも含み、切り替えに費やした時間そのものは測っていない。
このコマンドが表示するのは総数だけなので、実行時間が大きく異なる試行をそのまま比べない。
長い試行へ広げる場合は測定時間も保存し、毎秒あたりの回数を求める。

## 実測例で出力を読む

Apple M5 上の 4 vCPU の教材 VM（Ubuntu 26.04、Linux `7.0.0-30-generic`、scx 1.1.3）で、2026 年 9 月 6 日に測定した例を示す。
これは一回の参考記録であり、同じ数値になることを成功条件にはしない。
[2 秒スライスの全標本と測定条件](../measurements/2026-09-06/long.txt)も参照できる。

```text
sample,late_ms,deadline_missed
1,2462.364,true
2,1462.380,true
3,462.381,true
```

最初の標本は予定より約 2.46 秒遅れている。
次の二つは遅れが約 1 秒ずつ減り、負荷生成器が過ぎた予定時刻の分を続けて記録したことが読み取れる。
この三行を「別々の起床で、それぞれ約 2.46 秒、1.46 秒、0.46 秒 CPU を待った」とは解釈しない。

集計では次の結果になった。

```text
average_late_ms=1865.578
max_late_ms=3468.367
deadline_misses=15/15

               177      context-switches
```

この試行では全 15 標本が許容を超え、最大で約 3.47 秒遅れた。
`177` は CPU 0 全体の切り替え回数である。
同じ条件で取った [fair class のログ](../measurements/2026-09-06/fair.txt)では、最大遅延は 1.686 ミリ秒、deadline miss は 0 / 15 だった。

## 予想と突き合わせる

単一 CPU の FIFO で hog 二つだけが先行するモデルでは、runnable 後の待ちは最大で約 4 秒になる。
実行中の hog A の残りスライスと、すでにキューで待っている hog B のスライスを、最大 2 回分待つためである。
スライスを使い切った hog A は末尾へ並び直すので、そのときすでに待っている periodic を追い越さない。

```text
t=0                    t=2                    t=4
 |----------------------|----------------------|
 hog A:  残りスライスを実行
                         hog B: 1スライス実行
 periodic: runnable ---------------------------------> 実行
           <------------- 最大約4秒の待ち ----------->
```

この図は実測ログではなく、runnable になった瞬間を原点にしたモデルである。
2 秒のスライスを使い切る直前に periodic が起きれば、最初の待ちは短くなる。
また、割り込みやほかのスケジューラクラス、ホストの都合で VM が停止する時間は、この 4 秒に含めていない。
`late_ms` の厳密な上限として使う値ではない。

自分のログでは、fair class より遅れが大きくなったか。
数秒単位の遅れがあれば、長いスライスによる待ちという予想と整合する。
ただし、タイマー処理と dispatch 待ちを切り分けるには、[tail latency の章](../advanced/tail-latency.md)で扱うイベントのトレースが必要になる。
