# 1秒後に戻れないタスク

前章で、自分の scheduler が待ち行列を持ち、そこから CPU へタスクを送り出せるようになった。
ここからは、その方針がタスクの見える挙動をどう変えるかを調べる。

最初の問いは単純である。
`sleep(1)` を呼んだタスクは、1秒後に実行を再開できるのだろうか。
直感的には「1秒眠るのだから、約1秒後には戻ってくる」と考えたくなる。
しかし `sleep` が約束しているのは CPU の予約ではない。
この違いを、わざと極端な scheduler を使って見える形にする。

共有 DSQ は FIFO である。
先に入ったタスクのスライスが尽きるまで、後に入ったタスクは待つ。
この単純な性質が周期タスクに与える影響を、この章では数値で確かめる。

`sleep(1)` は「1秒後に CPU をもらえる」という命令ではない。
約1秒後にタイマーが満了すると、眠っていたタスクは再び runnable になる。
そこから実際に命令を再開するまでには、scheduler がそのタスクを選び、CPU へ dispatch する段階が残っている。
普段の Linux ではこの差が小さいため意識しにくいが、scheduler の方針を極端にすると、タイマーの満了と実行再開が別の出来事であることを目で追える。

この章で2秒という非常に長いスライスを使うのも、そのためである。
2秒スライスを実用的な設定として勧めたいわけではない。
小さな差を精密に測る代わりに、原因と結果が数秒単位で現れるように現象を増幅し、FIFO とタイムスライスだけで遅延を説明できる状態を作る。
まず極端な条件で因果関係を確認し、そのあと現実的な値へ戻すのが、この実験の狙いである。

これは性能ランキングを作るための benchmark とは少し目的が違う。
ここで欲しいのは「何ミリ秒速いか」という精密な数字より、一つの設計変更がどの観測値を動かしたのかを説明できる条件である。
そのため、CPU affinity、タスク数、キュー構造を固定し、タイムスライスだけを変える。
この実験の作法は、後の章でも繰り返す。

## 実験の条件

実験では、二つの CPU-bound タスクと1秒周期のタスクを CPU 0に固定する。
`taskset` は scheduler を変更しない。
プロセスが実行できる CPU を CPU 0だけに制限し、三つのタスクが同じ CPU を奪い合う条件を作る。
CPU-bound タスクを二つにするのは、タイムスライスの切れ目でコンテキストスイッチが発生する状況を確実に作るためである。
交互に走る相手がいなければ、スライスを短くする効果が観測できない。

## 予想

ベンチマークを回す前に、結果を予想しておく。
スライスが2秒のとき、1秒周期のタスクは起床後、最大で約何秒待つことになるだろうか。
共有 DSQ が FIFO であることを使えば、紙の上で答えを出せる。
答えは、実測の後で突き合わせる。

## 2秒のスライス

```console
make restore STEP=03
```

この checkpoint は、dispatch 時に渡すスライスを2秒へ変更している。
コードの変更は定数一行だけである。

```c
const volatile u64 slice_ns = 2000000000ULL;  /* 2 seconds */
```

## ベンチマークを実行する

まず、`sched_ext` を使わずに負荷生成器を動かす。
fair class で同じ実験を回し、比較対象となる数値を取る。

```console
make bench CASE=fair
```

続いて、長いスライスの scheduler を使う。

```console
make bench CASE=step STEP=03
```

`make bench` は、上に書いた実験条件をすべて自動で再現する。
cpu-hog サブコマンドを CPU-bound タスクとして20秒間、CPU 0に固定して二本起動し、periodic サブコマンドを1秒周期で15回起床させる。
`CASE=step` では負荷生成器を `--sched-ext` 付きで起動し、partial mode の自作 scheduler の対象に入れる。
`CASE=fair` では自作 scheduler をロードせず、同じ CPU affinity と workload だけを再現する。

`make bench` は scheduler と workload のビルド、ロード、有効化の確認、実験後の停止までをまとめて行う。
別の端末で `make run` を起動しておく必要はない。

periodic workload は各起床について、予定時刻から実際に処理を再開するまでの遅れと、100ミリ秒の許容を超えたかを示す deadline miss を出力する。
最後に `perf stat` が CPU 0の context switch 数を表示する。

ここでは、出力の具体的な数値を「正解」として固定しない。
VM はホスト側の scheduling の影響も受けるためである。
見るべきなのは、同じ環境の中で条件を一つだけ変えたときに、遅延と context switch がどちらへ動いたかである。

## 観測の読み方

15標本では p95 や p99 を安定して評価できない。
ここで比べるのは、個々の遅延、最大遅延、deadline miss 数である。
標本数を増やして分布の裾を見る方法は、発展編の tail latency の章で扱う。

## 予想と突き合わせる

2秒スライスのとき、周期タスクの最大遅延は理論上、約4秒まで伸びうる。
スライスが尽きた hog は、FIFO の末尾へ2秒のスライス付きで並び直す。
周期タスクが起床した時点で、実行中の hog の残りスライスと、キューに並んでいるもう一方の hog のスライスの、最大2回分を待ちうるからである。

周期タスクが runnable になった瞬間を `t=0` とすると、最悪に近い場合は次のように考えられる。

```text
t=0                    t=2                    t=4
 |----------------------|----------------------|
 hog A:  残りスライスを実行
                         hog B: 1スライス実行
 periodic: runnable ---------------------------------> 実行
           <------------- 最大約4秒の待ち ----------->
```

実際の起床位置はスライス境界と一致するとは限らないので、毎回4秒待つわけではない。
この図は「最大で何を待ちうるか」を説明するためのモデルである。
最大遅延と deadline miss が、この説明と整合するか確かめる。
`sleep(1)` がタイマーを遅らせたのではなく、タイマー満了後の dispatch が遅れた、というのがこの章の結論である。

ここで見ているのは、単に「悪い scheduler を作ると遅くなる」という話ではない。
CPU-bound な処理にとって長いスライスは、途中で止められる回数を減らせる一方、途中から runnable になったタスクには長い待ち時間を押し付ける。
同じ設定が workload によって利点にも欠点にもなる。
スケジューラの評価では、平均的にどれだけ CPU を使えたかだけでなく、「起きたタスクをどれだけ早く再開させたいか」という応答性の要求も別に考える必要がある。
